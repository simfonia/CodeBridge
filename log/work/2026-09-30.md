### CB-T2：心跳測試改用注入式可控計時器（P1）

**問題**：`ui/tests/unit/compile-controller.test.js` 的「上傳期間心跳確實會跳（每秒一個點）」
真的 `await new Promise(r => setTimeout(r, 1100))` 等兩輪，單獨耗 **2227ms**，佔單元套件 2.86s 的 **78%**。

**第一次嘗試失敗（重要技術發現）**：先改用 `vi.useFakeTimers({ toFake: ['setInterval','clearInterval'] })` ＋
`await vi.advanceTimersByTimeAsync(1100)`，結果測試**變紅**（`dots` 為 0）。
根因在 `ui/tests/support/classic-script.js` 第 19 行：
```js
const sandbox = { console, setTimeout, clearTimeout, setInterval, clearInterval, ...globals };
```
計時器是**在 sandbox 建立時依值複製**進 vm context 的，因此偽造 `globalThis.setInterval`
對「已載入的 sandbox」完全無效——控制器在 sandbox 內呼叫的是載入當下那份**真實**計時器。
> 這也解釋了該檔註解「sandbox 缺 setInterval → 守占說未動」的歷史教訓。

**最終解法**：在**載入時**注入可控計時器，測試手動觸發，完全不靠時間。
1. `loadController()` 新增 `setup.timerGlobals`，透傳給 `loadClassicScript(path, globals)`（`globals` 在預設計時器之後展開，故可覆寫）。
2. 測試注入 `setInterval`（記錄 callback 與 delay）與 `clearInterval`（清除 callback 並計數）。
3. 斷言強化為：心跳已啟動（`ticks.fn` 為 function）＋ **間隔確為 1000ms** ＋ 每次觸發補一點（`+2`）＋ 收到上傳終態事件後 `clearInterval` 被呼叫且 callback 釋放、點數不再增加。

**過程中抓到第二個 bug**：原本以「含點的記錄數」計數，但終端機的 `appendToLast` 會把點**併進同一筆記錄**，
兩次心跳落在同一筆 → 期望 2 實際 1。改為計算**實際點字元數**（`split('.').length - 1` 累加）後正確。

**紅→綠→再紅三段驗證（防假綠）**：
| 階段 | 手段 | 結果 |
|---|---|---|
| 綠 | 新實作 | 37/37 通過，2390ms → **210ms** |

### 技術深挖 (Technical Deep Dive)

**Q：為什麼 `vi.useFakeTimers()` 在本專案的單元測試會失效？**
前端是 classic script（非 ESM），測試以 `node:vm` 建立獨立 context 載入。
`classic-script.js` 在建立 sandbox 物件時把 `setTimeout/clearTimeout/setInterval/clearInterval`
以**當下的值**複製進去，因此：
- sandbox 內的控制器呼叫的是真實計時器
- 之後才呼叫 `vi.useFakeTimers()` 只會偽造 vitest 自己的 globalThis，對已載入的 context 無效
- **正確做法**：在 `loadClassicScript(path, globals)` 的第二個參數注入自訂計時器
  （`globals` 排在預設計時器之後展開，天然具覆寫優先權）
此陷阱已寫入 `AGENTS.md` 計時器紅線，避免下一輪再次踩坑。

**Q：注入可控計時器會不會讓測試「變弱」？**
不會，反而變強：原本只斷言「1.1 秒後至少有一筆含點的記錄」，
現在可斷言**心跳確實以 1000ms 間隔註冊**、**每跳一次補一點**、**收到終態事件後 clearInterval 被呼叫**，
且完全不依賴真實時間，無 flake 風險。

**Q：為何 L2 只放兩支 Blockly spec？**
`playwright.config.mjs` 為 `workers: 1` + `fullyParallel: false` + system Edge，全量 14 支需數分鐘。
`blockly-runtime` 與 `blockly-migration` 正是 AGENTS.md 指定的 TDD Red 起點與積木契約核心，
是最值得日常升級的兩支；其餘互動型 spec 留給 L3／CI。

## #task[CodeBridge CI] CB-T5 ＋ CI 拆 unit/e2e ＋ run #12 失敗分析（2026-09-30）

### CB-T5：雜訊的真因不是 log，是每次跑測試都在複製整個 src
`[Vite] Copying static folder: src -> dist/src` ×3 的來源是 `ui/vite.config.js` 的
`copyCodeBridgeAssets` plugin。該 plugin 只有 `closeBundle` hook、**沒有 `apply` 限制**，
因此 vitest 每次結束（vite server close）都會觸發它 → 每次跑測試都把
`ui/src/` 與 `ui/blockly/` **遞迴複製進 `ui/dist/`**（`fs.cpSync(..., { recursive: true })`）。
也就是說這不只是「輸出髒」，而是**每次跑 261 個測試都白做一次完整目錄複製**。

修正：加 `apply: 'build'`，只在 `vite build` 生效。
驗證（先刪掉整個 `ui/dist` 再重跑 build，確保不是舊檔殘留）：
- `npm run test:unit` → 無 `[Vite]` 輸出，261/261，662ms
- `npm run build` → **仍正常**：`dist/index.html` ✅、`dist/src` ✅、`dist/blockly` ✅
  （Tauri 打包依賴 `dist/src` 與 `dist/blockly` 的原始目錄結構，不可回退）

### CI 拆分 unit／e2e（決策點 1）
```yaml
unit:              4 steps  → npm ci → npm run test:unit（Vitest 261 例／約 0.7s）
blockly-contract:  needs: unit, 7 steps → npm ci → test:blockly:assets → test:e2e → build → 上傳 report
```
- 兩者皆**阻塞式**（未採 `continue-on-error`／nightly），任一紅燈即整體失敗。
- 代價：兩個 job 各自 `npm ci`；由 `setup-node` 的 `cache: npm` 抵銷大部分時間。
- 效益：邏輯層回歸 ~10 秒內就能看到，不必等 Playwright 跑完；且 job 名稱直接指明是哪一層壞掉。

### run #12 失敗分析與修復（使用者提供日誌後定案）

**症狀**：`npm error code EUSAGE` —「`npm ci` can only install packages when your package.json and package-lock.json … are in sync」，
並列出 `Missing: @emnapi/core@1.11.3 from lock file`、`Missing: @emnapi/runtime@1.11.3 from lock file`。

**根因**：`ui/vite.config.js` 走 Vite 8 → `rolldown`，而 `rolldown` 有 15 個平台專屬 `optionalDependencies`，
其中 `@rolldown/binding-wasm32-wasi`（`cpu: ["wasm32"]`，win32 **永遠不會安裝**）依賴
`@emnapi/core@1.11.1` / `@emnapi/runtime@1.11.1`。舊的 `ui/package-lock.json` 只把這兩者記在
**巢狀路徑** `node_modules/@rolldown/binding-wasm32-wasi/node_modules/@emnapi/*`，
頂層並不存在。

| npm 版本 | 對同一份 lock 的 `ci` 驗證 |
|---|---|
| **11.6.2**（本機 Node 24.12.0） | ✅ 通過 |
| **11.19.1**（CI 當時的 Node 24 所附） | ❌ `EUSAGE`，要求頂層 `@emnapi/core@1.11.3` |

workflow 寫的是 `node-version: 24`（**浮動**），npm 隨 Node 24 小版本升級而改變驗證邏輯，
於是「本機綠、CI 紅」。這也解釋了為何 4 秒就 exit 1：`npm ci` 在下載前先做 lock 驗證，直接擋下。

**修復（選用重建 lock 而非 pin Node）**：
```
npx -y npm@11.19.1 install --package-lock-only   # 用新版 npm 重建
```
diff 僅 **+28 / −3**：
- 新增頂層 `node_modules/@emnapi/core@1.11.3`、`@emnapi/runtime@1.11.3`（標記 `peer` + `optional`）
- 頂層 `@emnapi/wasi-threads` 標記為 `peer`
- 順帶修正 lock 根節點過時的 `version: 0.1.0 → 0.2.0`（與 `package.json` 不符）

**雙版驗證**（這是重點——不能只在新版 npm 上驗過就算）：
