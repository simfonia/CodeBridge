## 行尾（CRLF/LF）三層防護機制移植

### 背景
自 Cocoya 專案移植行尾檢查機制到 CodeBridge。但**不能直接照抄** —— 兩專案的行尾基準與例外結構不同。

### 現況調查（移植前實測）
- `git ls-files --eol`：214 個受追蹤檔中 **184 個 w/crlf、24 個 w/lf、6 個 w/mixed**。
- 危害最高的是 **6 個混合行尾**：
  `log/plan/BlocklyV13MigrationExperience.md`、`log/plan/SettingsCenterAndCoreSharing.md`、
  `log/work/2026-07-27.md`、`log/work/2026-09-25.md`、
  `ui/src/theme/code-theme-adapter.js`、`ui/src/theme/presets.js`。
- 另 4 個純 LF 的真問題：`ui/src/lib/i18n/{en,zh-hant}.js`、`src-tauri/src/arduino/pipeline.rs`、`src-tauri/src/serial_monitor.rs`。

### 與 Cocoya 的三處關鍵差異（移植時刻意調整）
1. **行尾基準不同**：Cocoya 為 `* text=auto eol=crlf`（全專案 CRLF）；
   CodeBridge 的 `.gitattributes` 沿用 `text`（各平台慣例），且 **`*.cbg` 依 SPEC.md §3 必須是 LF**。
   → 工具不能只會「轉成 CRLF」，必須理解「必須維持 LF」的例外。
2. **位元組鎖定資產**：`ui/public/blockly/**` 由 `VERSIONS.md` 以 bytes/SHA-256 鎖定
   （2026-09-30 run #13 曾因此紅燈，已標 `-text`）。
   → 必須完全跳過，且此規則須在 `.gitattributes` 最後（屬性後者勝出）。
3. **工具產物**：`src-tauri/icons/**` 為 Tauri CLI 生成（`tauri icon` 會重新產生）。

### 技術深挖 (Technical Deep Dive)

#### 自我驗證機制是本次移植最大的收穫
`scripts/eol.mjs` 內建 `verifyAgainstGit()`：以 `git ls-files --eol` 交叉比對，
抓出「git 認定工作區為 LF/mixed，但本工具沒掃到」的檔案。

**這道守門立刻發揮作用**：第一版掃描範圍遺漏了 4 個檔案
（`src-tauri/Cargo.toml`、`Cargo.lock` 與兩個 Android icon XML），交叉比對直接點名。
其中 `Cargo.lock` 是 4756 行、為主要不一致來源。
若沒有這道，工具會「全綠」卻漏掉真正的問題 —— 這正是 Cocoya 版同樣強調的設計。

#### 一個被推翻的無憑據假設
初版我把 Android icon XML 加進 `MUST_LF_BASENAMES`（憑印象認為「Android 資源理應是 LF」）。
查證後發現 `src-tauri/icons/**` 是 **Tauri CLI 產生的資產**，專案規範從未要求其行尾
（AGENTS.md / SPEC.md 完全未提及 icons）。
→ 移除該假設，改列入 `BYTE_LOCKED` 跳過，並在 AGENTS.md 明寫「新增例外前必須有憑據」。

**教訓**：無憑據的排除會讓真問題被永久忽略，比沒有守門更糟。

#### CI 為何只在 windows-latest 跑 eol job
本專案 `.gitattributes` 用 `text`（各平台慣例）。若把 eol job 加入跨平台矩陣，
macOS/Linux runner checkout 會得到 LF，**全數報紅（假紅燈）**。
故只在 `windows-latest`（`core.autocrlf=true`，與開發環境一致）執行。
另：eol job **不需安裝前端依賴**（只用 Node 內建模組），故不寫 `npm ci`。

### 追加：`.cbg` 行尾的兩次追問與查證（同日）

使用者連續追問兩題，逐一查證後決定**維持 LF**：

#### 追問一：「程式執行不受行尾影響，為何 `.cbg` 不能也用 CRLF？」

**關鍵發現：不是規格好聽，是程式碼在強制寫。**

`src-tauri/src/project.rs` L67（`project_save`，Tauri command）：
```rust
let normalized = contents.replace("\r\n", "\n").replace('\r', "\n");
```
任何呼叫端寫入的 CRLF，存檔瞬間都被轉回 LF。

> **決定性後果**：若只改三層設定而不同改程式，`eol:check` 會對 3 個範例檔**永遠報紅**，
> 開發者無論怎麼修都修不好（存檔又被轉回去）。這比原狀態更糟。
> 要改就必須連程式、測試斷言、SPEC.md 一起改 —— 屬產品決策。

另一反對理由：`*.cbg` 選 LF 應是為**跨平台一致性**，改成 CRLF 會讓格式變 Windows 專屬。

實測確認既有測試 `project::tests::save_then_read_round_trips_without_bom` **刻意用 CRLF 輸入**（L151）
並斷言讀回是 LF（L155）—— 是**設計**不是巧合。`cargo test` 實測 16 passed。

#### 追問二：「用文字編輯器改 `.cbg` 變成 CRLF，CodeBridge 開得起來嗎？」

**三層實測，結論：開得起來，且會自我修正。**

| 層 | 實測結果 |
|---|---|
| `parse()`／`findRootTag()` | ✅ `format=1`、屬性 `[format=1, name=Blink]` 與 LF **完全相同**（根元素同行，正則不受行尾影響） |
| `DOMParser`（`textToDom`） | ✅ `parse error: none`，`block id` 正常。**XML 1.0 規範要求 CRLF 正規化為 LF**，實測重新序列化不含 `\r` |
| `project_save` | ✅ 自動轉回 LF |

**⚠️ 唯一的真實風險是 git 假變更**（不是開不起來）：不支援 `.editorconfig` 的編輯器
（Windows 記事本等）改完後，git 會顯示 `.cbg` modified 但內容一字未改。`eol:fix` 可修。

**防範**：`.editorconfig` 的 `[*.cbg] end_of_line = lf` 讓 VS Code 等支援者在**存檔當下**維持 LF。
