### 技術深挖 (Technical Deep Dive)

#### 死碼 `Operation.child`：兩條 kill 路徑的誘惑
T1 留下的 `child: Option<Arc<Mutex<Child>>>` 從未被讀寫。若照著它的直覺去「接上」就會出現兩個問題：`Child` 無法安全跨執行緒共享（`kill` 需要 `&mut`），而且會與串流 runner 內部的 kill 形成兩條路徑 —— 誰先殺、狀態怎麼回報都會分歧。串流 runner 的設計已經讓執行緒自己持有 `Child` 並輪詢 cancel 旗標，因此正確做法是**刪掉**這個欄位，而不是接上它。

#### 節流策略要獨立成純函式
`EventSink` 需要 `AppHandle` 才能測試。把「該不該 flush」抽成 `FlushPolicy::take_flush()` 後，節流行為可在沒有 Tauri app 的情況下完整驗證（時間門檻、行數門檻、flush 後重置），`EventSink` 只剩薄薄一層 emit。

#### 上傳必須佔用序列埠
兩個作業同時對同一個 COM 埠跑 `avrdude`，結果是第二個必然失敗，且錯誤訊息難以診斷。`port_lease` 在 `upload_start` 取得、**無論成功與否都釋放**，並對同一埠冪等（避免重複點擊自我阻塞）。

### 技術深挖 (Technical Deep Dive)

#### 實測推翻了 `--json` 的三項假設
1. **`--json` 模式下 stderr 完全為空**。原本假設「stdout 收最終 JSON、stderr 收進度」，實測連進度都被包進 JSON 物件，終端機面板會一片空白。改用非 JSON 模式後分工正好符合需求：stdout 是人類可讀摘要（`Sketch 使用 1918 位元組（5%）`），stderr 是 gcc/avrdude 診斷（`path:line:col: error: msg`），後者正是既有 `diagnostics.rs` 的解析格式。
2. **成功判定改用結束碼**。非 JSON 模式沒有 `success` 欄位，但 `exit=1` 可靠。取消與逾時分支必須**先於**成敗判斷，否則使用者會看到「編譯失敗」而非「已取消」，且會錯誤保存 build 紀錄。
3. **`used_libraries` 取不到**。該欄位只在 `--json` 回應中；非 JSON 模式下沒有，因此本輪移除該欄位（留待後續機制），避免留下永遠為空的誤導 API。

#### 成功編譯時 stderr 仍有警告
實測 `arduino:avr` 成功編譯時，stderr 含有 avr 核心檔 `new.cpp` 的 unused parameter 警告。後端必須**原樣保留**並附上檔名，UI 才能依 `diag.file !== inoFileName` 決定是否跳轉 —— 若後端過濾掉，使用者會看不到自己草稿的警告。

#### locale 會改變訊息文字，解析不可依賴字面
arduino-cli 的訊息跟著系統 locale（繁中顯示「建構時出錯」「Sketch 使用 …」）。因此 `parse_size_report()` 改用與語言無關的結構特徵（一行含數字緊接 `%`），而非比對「Sketch uses」等英文字串。這也是 `encoding.rs` 必須存在的原因：父端絕不能因為不是 UTF-8 就丟掉整份輸出。

#### 整合測試抓到兩個單元測試抓不到的 bug
1. **`command::version()` 漏掉子命令 token**（T1 遺留）：arduino-cli 收到全域旗標但沒有子命令，會印出整頁 help 並以 **exit 0** 結束。T1 的測試只斷言 `--format` 存在，因此完全漏掉。已補 `every_builder_passes_its_subcommand_token` 逐一驗證所有 builder。
2. **串流 runner 在子程序結束瞬間遺失最後幾行**：`try_wait()` 回報結束時，reader 執行緒仍有「在途的行」未送進 channel，`drain_remaining` 只抽得出已送達的部分。症狀是 `version`（6 行輸出、結束極快）回傳**空 stdout**，而 `board list` 正常 —— 典型的時序競爭。修法是結束前**先 join 所有 reader 再抽乾**。這個 bug 在只有假 runner 的單元測試中不可能出現。

#### Rust 字串續行的陷阱
測試內嵌 Python 腳本時，`\` 續行會吞掉下一行的**前導空白**，足以讓 Python 縮排失效而讓測試「測不到東西」（exit code 1、stdout 為空）。改用 `concat!` 後問題消失。凡是需要保留縮排的內嵌腳本都應避免續行字串。

### 技術深挖 (Technical Deep Dive)

#### 色碼反查是脆弱的識別機制
舊 `applyPalette()` 先把 `*_HUE` 寫回 `Blockly.Msg`，再建立 `sourceColours` 對照表（舊色碼 → 新色碼），最後以 `block.getColour()` 反查。問題在於 colour 是執行期狀態而非識別碼：若使用者或第三方模組把 block 顏色改成另一模組的色碼，切換 preset 時該 block 就會被錯誤地染成「原色碼對應的角色」顏色。改用 `block.type` 作為識別碼後，顏色是 block 的純函式結果，與執行期狀態無關。

#### Variables 分類沒有固定 block，必須有分類層的語意
舊實作只對「分類內含 block」的情況對齊色塊，Variables 是 `custom="VARIABLE"` 的 dynamic 分類，XML 內沒有 block 節點，因此永遠保持原色，Engineer／Angel 下不一致。改用 `CATEGORY_ROLES` 直接由分類名稱（`%{BKY_VARIABLES_CATEGORY}`）推導語意角色，dynamic 分類也能對齊。分類色塊的優先順序為「分類內第一個 block 的 role → 分分類語意」，以維持既有 Engineer toolbox 視覺 contract。

#### 舊 message key 必須保留
Blockly 13 在 block 建立時解析 `colour: '%{BKY_XXX_HUE}'`，全數 45 個模組 block 定義都用此機制。若直接把色碼搬離 locale 而不做同步，之後從 toolbox 拖出的新 block 會拿到 locale 檔中的靜態舊色碼。`syncLegacyHueMessages()` 在每次 `applyPalette()` 時把語意色碼寫回 `Blockly.Msg[KEY]` 與 `Blockly.Msg['BKY_'+KEY]`，使舊定義與新 contract 同時成立，遷移可分階段進行。

#### 精確規則必須優先於前綴規則
`controls_` 前綴對應 logic，但 `controls_for`／`controls_while`／`controls_flow_statements` 屬於 loops；`arduino_delay` 同時命中 `arduino_` 系列與 time 語意。`getRoleForBlockType()` 依序檢查「第三方註冊 → 精確 TYPE_ROLES → 第三方前綴 → 內建前綴」，確保例外不需特例程式碼。

### 技術深挖 (Technical Deep Dive)

#### jsonInit 只接受字串
`jsonInit()` 的參數物件會先被 `Blockly.utils.replaceMessageReferences()` 以字串取代佔位符，因此無法在參數物件內呼叫 `getColourForRole()`。顏色必須在 `jsonInit()` 之後以 `this.setColour()` 設定。這也是移除 `colour: '%{BKY_XXX_HUE}'` 機制後唯一的可行做法。

#### Blockly 官方 msg 自帶同名 key
`ui/public/blockly/msg/en.js` 與 `zh-hant.js` 本身定義了 `LOGIC_HUE = "210"`、`MATH_HUE`、`VARIABLES_HUE` 等 key（值為數字色碼，供 Blockly 內建 style 使用）。這些與 CodeBridge 模組原本定義的同名 key 語意不同，刪除模組定義後仍會存在於 `Blockly.Msg`。因此驗證「語系檔已無 `*_HUE`」時須改用 CodeBridge 專屬的 key（如 `ARDUINO_DIGITAL_IO_HUE`、`LOGIC_COMPARE_HUE`）作為斷言依據。

#### 應用程式不主動清除舊 localStorage 鍵
移除遷移邏輯後，舊的 `codebridgeTheme` 仍會留存在使用者瀏覽器。應用程式只單純忽略它，不讀取也不寫回；由瀏覽器自然淘汰。刻意加入清除反而是無意義的額外行為。

### 技術深挖 (Technical Deep Dive)
- **按鈕責任歸屬（與初版計畫的刻意偏離）**：`#btn-terminal` 與三顆終端機工具列按鈕都帶 `data-action`，
  點擊已由 `toolbar.js` 的 document 委派統一處理。若 `terminal-panel.js` 再 `addEventListener`，
  同一次點擊會觸發兩次（開 -> 關），按鈕看起來像壞掉。因此面板只提供純方法，**不綁定 click**，
  並以單元測試鎖定此契約。
- **`compileOperationId` 與 `activeOperationId` 必須分離**：`upload_start` 會覆寫 `activeOperationId`，
  但後端 `compile-diagnostics` 事件仍帶編譯作業的 id。若只比對 `activeOperationId`，
  上傳開始後回來的編譯診斷會被整批丟棄。`isOwnOperation()` 同時接受兩者，且事件未帶 id 時視為相關。
- **`projectId` 必須截斷到 64 字元**：後端正則 `^[A-Za-z0-9_-]{1,64}$`，超長專案名會被
  `DRAFT_ERROR_INVALID_PROJECT_ID` 拒絕。單元測試抓到未截斷的缺陷，已加入 `MAX_PROJECT_ID_LENGTH`。
- **只標記自己草稿的診斷**：gcc 成功編譯時也會回報函式庫核心檔的警告，那些行號與使用者程式碼無關，
  標記了只會誤導。依檔名過濾後才標記，並在套用前清除前一次標記。
- **分塊建立檔案的插入點陷阱**：`insert_line` 插在該行「之前」，多次分塊寫入容易吃掉原本的結尾大括號，
  造成語法仍合法但 `test()` 被巢狀在未閉合的函式內（vitest 顯示為 `No test found in suite`）。
  每個新檔案都以 `node --check` + 括號深度檢查驗證。
- **`stop` 的語意**：T2 階段沒有常駐程序可停，「停止」= 取消進行中的編譯或上傳作業
  （`operation_cancel`），tooltip 由 `TLB_STOP_HINT` 說明；序列監視器屬 T3。
