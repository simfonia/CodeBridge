### 技術深挖 (Technical Deep Dive)

#### 色碼反查是脆弱的識別機制
舊 `applyPalette()` 先把 `*_HUE` 寫回 `Blockly.Msg`，再建立 `sourceColours` 對照表（舊色碼 → 新色碼），最後以 `block.getColour()` 反查。問題在於 colour 是執行期狀態而非識別碼：若使用者或第三方模組把 block 顏色改成另一模組的色碼，切換 preset 時該 block 就會被錯誤地染成「原色碼對應的角色」顏色。改用 `block.type` 作為識別碼後，顏色是 block 的純函式結果，與執行期狀態無關。

#### Variables 分類沒有固定 block，必須有分類層的語意
舊實作只對「分類內含 block」的情況對齊色塊，Variables 是 `custom="VARIABLE"` 的 dynamic 分類，XML 內沒有 block 節點，因此永遠保持原色，Engineer／Angel 下不一致。改用 `CATEGORY_ROLES` 直接由分類名稱（`%{BKY_VARIABLES_CATEGORY}`）推導語意角色，dynamic 分類也能對齊。分類色塊的優先順序為「分類內第一個 block 的 role → 分分類語意」，以維持既有 Engineer toolbox 視覺 contract。

#### 舊 message key 必須保留
Blockly 13 在 block 建立時解析 `colour: '%{BKY_XXX_HUE}'`，全數 45 個模組 block 定義都用此機制。若直接把色碼搬離 locale 而不做同步，之後從 toolbox 拖出的新 block 會拿到 locale 檔中的靜態舊色碼。`syncLegacyHueMessages()` 在每次 `applyPalette()` 時把語意色碼寫回 `Blockly.Msg[KEY]` 與 `Blockly.Msg['BKY_'+KEY]`，使舊定義與新 contract 同時成立，遷移可分階段進行。

#### 精確規則必須優先於前綴規則
`controls_` 前綴對應 logic，但 `controls_for`／`controls_while`／`controls_flow_statements` 屬於 loops；`arduino_delay` 同時命中 `arduino_` 系列與 time 語意。`getRoleForBlockType()` 依序檢查「第三方註冊 → 精確 TYPE_ROLES → 第三方前綴 → 內建前綴」，確保例外不需特例程式碼。

### 技術深挖 (Technical Deep Dive)

#### jsonInit 只接受字串
`jsonInit()` 的參數物件會先被 `Blockly.utils.replaceMessageReferences()` 以字串取代佔位符，因此無法在參數物件內呼叫 `getColourForRole()`。顏色必須在 `jsonInit()` 之後以 `this.setColour()` 設定。這也是移除 `colour: '%{BKY_XXX_HUE}'` 機制後唯一的可行做法。

#### Blockly 官方 msg 自帶同名 key
`ui/public/blockly/msg/en.js` 與 `zh-hant.js` 本身定義了 `LOGIC_HUE = "210"`、`MATH_HUE`、`VARIABLES_HUE` 等 key（值為數字色碼，供 Blockly 內建 style 使用）。這些與 CodeBridge 模組原本定義的同名 key 語意不同，刪除模組定義後仍會存在於 `Blockly.Msg`。因此驗證「語系檔已無 `*_HUE`」時須改用 CodeBridge 專屬的 key（如 `ARDUINO_DIGITAL_IO_HUE`、`LOGIC_COMPARE_HUE`）作為斷言依據。

#### 應用程式不主動清除舊 localStorage 鍵
移除遷移邏輯後，舊的 `codebridgeTheme` 仍會留存在使用者瀏覽器。應用程式只單純忽略它，不讀取也不寫回；由瀏覽器自然淘汰。刻意加入清除反而是無意義的額外行為。
