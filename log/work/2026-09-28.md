### 技術深挖 (Technical Deep Dive)

#### 變數沒有型別定義：兩個獨立的根因

**使用者回報**：範例 3 產生的 .ino 沒有任何變數型別定義（`// Global variables` 是空的），
貼到 Arduino IDE 編譯必然失敗。

診斷分兩層，**第一層的假設是錯的**：

**第一層假設（錯）**：懷疑 generator 沒註冊或 `global_vars_` 沒組裝進 `finish()`。
實測卻發現——把宣告積木接在 setup 積木**內部**時，`int counter = 0;` 確實有產出。
generator 本身完全正常。

**第二層根因一**：`ui/src/main.js` 的 `updateOrphanBlocks()` 會掃描所有根層積木，
凡 type 不在 `Blockly.Arduino.scopeDefiningRootBlocks` 白名單內的，
連同其所有 descendants 一起 `setDisabledReason(true, 'orphan')`。
而 **`_core.js` 的白名單裡有 `array_declare_global` 卻漏了 `variables_declare_global`**。

**停用的積木不產生程式碼** —— 這是 Blockly 的既有行為，也正是「漂浮的
`arduino_delay` 不該被算進程式」的機制。症狀鏈：

```
使用者把宣告積木擺在根層（最自然的位置）
  → 不在白名單 → 被標記 orphan 而停用
  → generator 對停用積木不產碼
  → // Global variables 空
  → 無任何錯誤或警告
```

#### 對齊 piBlockly：定義堆疊模型（使用者第二次回報）

使用者指出：**沒有完全對齊 piBlockly 4 個變數積木，不該像當時那樣
「為每個變數產生個別積木」**。實際比對 `C:\Workspace\piBlockly\media\` 後確認差異：

piBlockly 的 `variables_declare_global` generator **不是**逐顆產碼，
而是 `processDefinitionStack`（`media/generators/_lib.js`）：

```js
Blockly.Arduino.forBlock['variables_declare_global'] = processDefinitionStack;
Blockly.Arduino.forBlock['coding_raw_definition']   = processDefinitionStack;
```

機制：

1. 宣告積木以 `next` 串成一條**連續堆疊**
2. 只有**堆疊最上方**的積木觸發 generator（判斷依據：`getPreviousBlock()` 是否為定義型）
3. 沿 `next` 走完整條堆疊，合併為 `global_vars_['stack_' + 堆頂id]` 的**單一 entry**
4. 非堆頂積木直接 `return ''`，避免重複產碼

`DEFINITION_BLOCK_TYPES = ['variables_declare_global', 'coding_raw_definition']`
—— **兩者共用同一條堆疊**，因為在 C++ 裡它們都是「全域宣告」，
可以合法混寫（`int x = 0;` 接 `const int LED = 13;`）。

CodeBridge 原先是「每顆積木各自 `global_vars_['variables_declare_global_' + name]`」，
是**不同的模型**。已完整移植（`DEFINITION_BLOCK_TYPES`、`globalVariableDefinition()`、
`processDefinitionStack()` 三者都放進 `_core.js`，兩個模組共用）。

**堆疊模型比逐顆模型的實際好處**

| | 逐顆獨立積木 | 堆疊（piBlockly） |
|---|---|---|
| 畫面 | 四顆散落的積木 | 一條連續的「型別宣告區」 |
| `global_vars_` | 四個 entry，順序不保相鄰 | 單一 entry，順序穩定 |
| 非堆頂積木 | 各自產碼，需額外去重 | 自動 `return ''` |
| 與 coding_raw_definition | 兩條互不相干的堆疊 | 可混在同一條 |

**順帶修正的細節**：`coding_raw_definition` 原本逐顆加 ID marker
（`user_definition_ + id`）。改為堆疊後逐顆加 marker 會與單一 entry 結構不一致，
改由堆頂積木的 marker 對應「這一整段宣告」。

**一個實測教訓**：`field_multilineinput`（`coding_raw_definition` 的 CODE 欄位）
不能用 `block.setFieldValue('CODE', ...)` —— 那是 dropdown／input 的 API，
會拋 `Field "..." not found`。正確做法是 `block.getField('CODE').setValue(...)`。

**「完全對齊」也要對齊到「不該照抄的地方」**：piBlockly 的
`processDefinitionStack` 寫入 `global_vars_` 時結尾有補 `'\n'`，直接照搬會讓
v12 migration 的 `variables.xml` fixture 失敗 —— 本專案 `finish()` 是以
`Object.values(...).join('\n')` 組裝各區段，多帶的 `\n` 會讓
`// Global variables` 之後多出一個空行。
**「對齊」指的是模型與行為一致，不是逐字複製** —— 差異處要理解成因再決定。

#### 變數分類：對齊 piBlockly 的固定 4 顆積木（使用者第三次回報）

使用者再次糾正：**「CodeBridge 現在是利用建立變數按鈕，然後動態產生該變數的操作積木，
而且全是全域的；piBlockly 永遠只有 4 個積木，而且有 global/local。」**

我前兩輪都改錯地方了 —— 一直在改 generator，實際問題在 **toolbox 結構**。

CodeBridge 原本（`ui/index.html:348`）：

```xml
<category name="%{BKY_VARIABLES_CATEGORY}" custom="VARIABLE"></category>
```

`custom="VARIABLE"` 觸發 Blockly 的 dynamic flyout 產生器
（`blockly.js` minified 的 `Fd`／`Ed`）：

```js
Fd = function(a) {
    a.registerButtonCallback("CREATE_VARIABLE", ...);
    return [{kind:"button", text:"%{BKY_NEW_VARIABLE}", callbackkey:"CREATE_VARIABLE"},
            ...flyoutCategoryBlocks(a, a.getVariableMap().getVariablesOfType(""))];
}
```

**Blockly 自動幫你產生按鈕，然後為每一個變數各生一對 `variables_get`／`variables_set`。**
這就是使用者說的「動態產生該變數的操作積木」。

症狀有兩層，第二層才是關鍵：

1. 變數一多，flyout 被同一批積木塞爆；
2. **`variables_declare_global`／`variables_declare_local` 永遠不會出現在 flyout** ——
   學生根本看不到「原來要先宣告型別」，於是產生的 .ino 沒有型別定義。

piBlockly（`piBlockly/media/toolbox.xml:301-307`）是固定 4 顆 + 按鈕，
並在 `main.js:924` 手動註冊 callback。

**改動只有兩處**

| 檔案 | 改動 |
|---|---|
| `ui/index.html` | `custom="VARIABLE"` → 固定 4 顆 + `<button callbackKey="CREATE_VARIABLE">` |
| `ui/src/main.js` | `createWorkspace()` 內 `registerButtonCallback('CREATE_VARIABLE', ...)` |

**為什麼改完後按鈕一定要自己註冊**：Blockly 的動態分類會**自動**註冊
（`Fd` 裡就有 `a.registerButtonCallback("CREATE_VARIABLE", ...)`），
但改用固定分類後按鈕改由 toolbox XML 宣告，Blockly 不再代勞。
不註冊的症狀是「點了按鈕完全沒反應」—— 沒有任何錯誤訊息。

**一個副作用是好的**：固定分類後這 4 顆積木正式進入 `block-palette.js` 的
palette 契約（`TYPE_PREFIX_ROLES` 有 `variables_: 'variables'`）。
原本 dynamic 分類下 toolbox 內沒有固定 block，
`theme-runtime.spec.js` 的斷言甚至刻意不含 `'variables'` —— 已一併修正。

**使用者明確要求「完全一致不加提示」**：建立變數後不額外提示使用者要去拖
`variables_get`。這是刻意的取捨 —— 對不熟悉積木的學生多一步，
但換來的是 flyout 永遠不會失控、宣告積木永遠看得到。

#### 範例 3 編譯失敗：變數名撞上 `math.h` 的函式（使用者實測）

使用者用真機編譯後回報：

```
error: 'int square' redeclared as different kind of symbol
note: previous declaration 'double square(double)'      ← math.h:203
error: assignment of function 'double square(double)'
```

**根因**：Arduino 的 `<math.h>` 定義了 `double square(double)`。C++ 規定全域命名空間裡
**識別字不能與已宣告的函式同名**，所以 `int square = 0;` 直接編譯失敗。

piBlockly 的 `addReservedWords` 同樣漏了 `square`（對照 `media/generators/_core.js:15`），
所以這是從 piBlockly 繼承來的缺陷。

**這一類問題特別難診斷**：產出的 `.ino` 本身完全合理、格式正確、程式邏輯無誤，
只有交給 `avr-gcc` 才會爆錯。使用者看到的是「CodeBridge 產生的程式碼編譯不過」，
但 CodeBridge 端完全沒有線索。

**兩處修正**

1. **範例 3 改名**：`square` → `squareValue`。
2. **補上 `addReservedWords`**：把 AVR `<math.h>`（`square`／`cube`／`hypot`／
   `fmod`／`round`…）、`<string.h>`、`<stdlib.h>` 的常見函式全部列入，
   讓 `field_variable` 的下拉選單能標示出這些名字已被占用。

**刻意沒有改的**：`text_join` 輸出的 `"square:"` label。

那是**字串常數**（序列繪圖的曲線名稱），不是識別字，與 `math.h` 無關；
而且它已被 plotter 測試鎖定為 `square:100, sine:50.00, noise:42`。
對學生而言曲線叫「方波 square」是直觀的，不該因為變數改名而一併改掉。
**識別字與輸出字串是兩件事** —— 這次差一點就把它們混為一談。

#### 示範專案 3 補上四個變數宣告（堆疊式）

除了修白名單，範例 3 本身也**完全沒有宣告積木**（只有 `variables_get` / `variables_set`），
所以即使白名單修好，這個範例產出的 .ino 仍舊沒有型別定義。已補上四個
`variables_declare_global`，擺在根層（`<variables>` 之後、setup 之前）。

**型別不是一律 int** —— 這裡有個會靜默產生錯誤結果的陷阱：

| 變數 | 型別 | 理由 |
|---|---|---|
| `angle` | `int` | 相位 0..360，遞增 5，整數剛好 |
| `square` | `int` | 只有 0 或 100 |
| `sine` | **`float`** | `50 + 50 * sin(...)` 產生小數。若用 `int`，賦值時被截斷成 0，`Serial.print` 永遠印出 0，正弦曲線會是一條死掉的直線 —— **程式「能編譯、能執行」，但圖是錯的** |
| `noise` | `int` | `random(0, 100)` |

`sine` 用 `int` 是最危險的一種 bug：不報錯、不崩潰，只是結果恆為 0。
已在 E2E 測試加上 `float\s+sine\s*=` 的斷言鎖住。

#### 為什麼 XML 註解在 Blockly 13.3.0 中會被靜默丟棄

`03_plot-waves.cbg` 原本的 6 項規格不符（詳見 `log/todo.md` 該章節「已完成」第 1 點），
其中真正有危害的是第 3、4 項。

Blockly 的 `domToWorkspace()` 透過 `mapSupportedXmlTags` 逐個檢查 child 節點的
tagName，只處理元素節點；註解節點（nodeType 8）不在任何 tag 的白名單裡，直接跳過。
`workspaceToDom()` 反向也不會產生註解。

**所以 `<!-- ... -->` 裡的文字在載入瞬間就從記憶體消失了，只存在於磁碟上的原始檔案。**
症狀是：使用者開啟範例 → 編輯 → 存檔，那 23 行教學說明與 8 處分節標記從檔案裡被洗掉，
**全程沒有任何錯誤或警告**。

對一個以教學為訴求的產品，這比「壞掉」更糟：作者以為說明會傳下去，
實際上第一位使用者就把它刪了，而且沒有人會知道。

因此改成：教學說明全部搬進 Blockly 的 `<comment>` —— 1 個工作區註解（掛在 `<xml>` 下）
放專案整體說明，7 個積木註解放各步驟說明，並統一 `pinned="true"`。

#### 為什麼直接用 Blockly 官方的 `domToPrettyText()`

Blockly 13.3.0 已提供 `Blockly.Xml.domToPrettyText(dom)`，實作（minified）為：

```js
domToPrettyText = (d) => {
  d = domToText(d).split("<");
  let indent = "";
  for (let i = 1; i < d.length; i++) {
    const part = d[i];
    if (part[0] === "/") indent = indent.substring(2);
    d[i] = indent + "<" + part;
    if (part[0] !== "/" && part.slice(-2) !== "/>") indent += "  ";
  }
  d = d.join("\n");
  d = d.replace(/(<(\w+)\b[^>]*>[^\n]*)\n *<\/\2>/g, "$1</$2>");
  return d.replace(/^\n/, "");
};
```

自己寫 formatter 只會產生**與 Blockly 輸出不同**的格式，範例檔與使用者存檔結果
就會分歧，出現「範例開起來是 A、存出來是 B」的幽靈差異。

`temp/pretty-cbg.mjs` 逐字複刻這個演算法（註明出處），用它產生三個範例檔，
再由 E2E 測試證明能被 Blockly 載入並產生預期程式碼。

**副作用**：註解文字不能含實際換行（會破壞縮排對齊），改用 `。` `；` 分隔。
這也讓教學說明在視覺上更緊湊，適合積木註解的大小。

#### metadata 注入與多行格式的相容性驗證

`project-store.js` 的 `findRootTag()` 用 `/<xml\b[^>]*>/` 找根標籤。
`[^>]*` 會跨行匹配，多行格式不會讓它抓不到根元素。

但 `serialize()` 是用 `text.replace(tag, injected)` 做**字串**替換 ——
若根標籤文字同時出現在內文（例如某個欄位剛好存了這段字串）就會誤替換。
`domToPrettyText` 產出的根標籤必定在第一行且獨一無二，因此安全。
新增測試「多行格式可注入 metadata，且根元素仍是第一行」把這點鎖成契約。

#### 為什麼需要 .gitattributes

規格要求 `.cbg` 以 LF 行尾落地，但專案原本沒有 `.gitattributes`。
在 Windows 上 Git 預設 `core.autocrlf=true`，會把索引內的 LF 轉成 CRLF 再寫回工作目錄，
於是「使用者存檔時產生 LF」與「git 取出後變成 CRLF」不一致：diff 全檔雜訊，
且 repo 內的檔案本身違反 SPEC.md §3.1。

Rust `project_save()` 會做 `replace("\r\n", "\n")` 正規化，所以**功能上**不會壞；
但那是掩蓋，不是修正 —— 讓版控層就守住規格才是正解。
加入 `*.cbg text eol=lf` 後，git status 不再出現 LF→CRLF 警告。

#### 修正 Vite 熱更新：改 `.cbg` 範例會整頁重載

使用者反應「修改 examples 會觸發 vite 熱更新」。檢查 `ui/vite.config.js` 發現兩個問題：

**問題一：忽略清單是反轉的。** 原本寫的是 `ignored: ['!**/dist/**']`。
這是**否定模式**（`!` 前綴），chokidar 會把它解讀為「排除這個清單之外的全都忽略」，
實際效果與註解寫的「不要監視 dist 目錄」**完全相反** —— 它在忽略整個 workspace，
只監看 dist。註解與行為不符，而且 HMR 行為不可預期。

**問題二：`src-tauri/resources` 完全沒被排除。**
Vite 的 `root` 雖是 `ui/`，但 watcher 會往上找 workspace root，
因此 `src-tauri/resources/examples/*.cbg` 的任何改動都會觸發 HMR。

這些 `.cbg` 是 Rust 端 `read_dir()` 掃描的 **Tauri bundle 資源**，
開發模式下前端根本讀不到（走 `read_example` IPC 從 Rust 端拿）。
重載頁面對它們毫無意義，**代價是使用者未儲存的積木布局被洗掉**。

修正為正向模式：

```js
ignored: [
  '**/dist/**',
  '**/src-tauri/resources/**',
  '**/src-tauri/target/**',
]
```

Rust 端的重新編譯由 Tauri CLI 自己的 watcher 負責，與 Vite 無關，不受影響。

### 技術深挖 (Technical Deep Dive)

#### 為什麼零 Rust 改動

`AppState::port_lease` 是單一持有者模型，`serial_monitor::Session` 與 `monitor_wants` 已經
把「租約協調 / 上傳暫停 / 自動重連 / 埠消失自動關閉」整套邏輯實測穩定化了。
Plotter 若在後端另開 plot session，就得複製這整套 —— 複製只會製造兩份會漂移的邏輯。

**Plotter 是 Monitor 資料流的圖形檢視，不是另一個裝置連線。** 這個定位讓整個功能只需要
在前端加一個訂閱點（`onDataLine`），Rust 端完全不必動、`cargo test` 零回歸。

#### 為什麼需要 `#terminalBody` 這一層包裝

`#terminalArea` 已經是 `flex column`：標題列與序列控制列在上，內容撐滿。
若直接把 `#plotPane` 放進 `#terminalArea`，會變成「標題 + 橫向雙欄 + 輸入行」錯位 ——
序列輸入行會橫跨兩欄，讓左欄不再是「純文字區」。

多包一層 `#terminalBody`，把「`#terminalContent` + `#serialInputBar`」綁成左欄、
`#plotPane` 綁成右欄，語意才乾淨。`terminal-panel.js` 全部用 `getElementById` 取得元素，
多包一層完全不影響既有程式碼與 `workspace-wheel.spec.js`（量的是 `terminalArea.offsetHeight`）。

#### 自動撐高與使用者拖曳高度必須分開記錄

兩種做法都會讓使用者覺得「面板在跟我作對」：
- 直接 `setHeight(320)` → 使用者拖到 500px 的高度被改掉
- 關閉時無條件還原 → 使用者在開繪圖期間手動調到 400px 也會被還原成 200px

因此只有**當我們自己執行過自動撐高**時才在關閉時還原，且只還原一次（`autoRaised` 旗標）。
單元測試明確斷言「高度已足夠時 open 不會覆蓋使用者的高度」與「close 只還原自己撐的那一次」。

#### 下抽樣用 min/max 對包絡而不是抽稀

常見的「每 N 點取 1 點」抽稀會讓**尖峰直接消失**。對感測器資料而言峰值往往正是使用者要找的東西
（「剛才那一下尖峰是什麼？」）。因此每個像素 bucket 拆成 min 與 max 兩點輸出，
畫面縮小時仍能看見訊號的完整輪廓。單元測試斷言 `expect(values).toContain(50)`（孤立高峰必須保留）。

#### 踩到的坑 1：IIFE 內的函式名稱會遮蔽全域同名變數

初版 `plot-render.js` 寫成：

```javascript
function devicePixelRatio() {
    if (typeof devicePixelRatio === 'number' && devicePixelRatio > 0) { ... }
}
```

函式宣告提升讓 IIFE 內的函式**遮蔽**了全域的 `devicePixelRatio` 變數，
因此 `typeof devicePixelRatio` 永遠拿到函式本身（不是 number），比例恆為 1。

症狀是「高 DPI 螢幕上線條糊掉」，但畫面上完全看不出成因。修正為 `readPixelRatio()` + `globalThis` 取值，
並在檔內註明**不可**命名為 `devicePixelRatio`。

#### 踩到的坑 2：圖例不該跟著 rAF 走

初版把圖例更新放在 `draw()` 裡（rAF 回呼），導致資料進來後圖例晚一幀才出現 ——
使用者會以為「資料進來了但沒畫出來」。

圖例反映的是**資料結構變化**（series 清單），不是像素重繪，必須同步更新；
只有 canvas 重繪才需要 rAF 節流。修正後 `handleDataLine` 內直接呼叫 `renderLegend()`。

#### 踩到的坑 3：時間戳必須留在終端機那一側

`onDataLine` 傳的是**未加時間戳**的原始行。帶上 `14:32:05.123 ` 前綴的話，
每一行都會被 parser 判為垃圾行而丟掉，圖表永遠是空的。單元測試明確斷言此契約。

#### 踩到的坑 4：混合行的取捨

`23.5, 開啟了, 40.2` 這種行：**只要有一欄有效就保留整行**，無效欄位以 `null` 表示（渲染時斷線）。
若整行丟棄，使用者會看到曲線莫名少了一段，卻完全不知道原因。

### 示範專案（03_plot-waves.cbg）：方波 + 正弦 + 隨機

Plotter 需要一個「一開啟就有東西看」的教學入口。每輪輸出 `square:100, sine:50.00, noise:42`，
繪圖會分成三條具名曲線。教學設計的三個刻意選擇：

1. **相位用看得見的 `angle` 變數，不用 `millis()`** —— 「週期由相位決定」若藏在 `millis()` 裡學生看不到
2. **先算波形、最後才推進相位** —— 讓每一筆資料都對應一個明確的角度
3. **三個值都落在 0..100** —— 正弦若用原生的 -1..1 會被方波壓成一條看不見的線

#### 踩到的坑 5：generator 支援 ≠ 積木有入口

`math_single` 的下拉選項只有 sqrt／abs／ln／log10／e^／10^，**沒有 sin** ——
但 `generators.js` 早就有 `case 'SIN'` 產出 `sin(x / 180.0 * PI)`。
有程式能力卻沒有 UI 入口，等於功能不存在。這類落差沒有任何編譯期錯誤，
因此補了一條 E2E 斷言專門守住選項清單。

#### 踩到的坑 6：Blockly 的 if/else 是互斥分支，後續步驟不能接在 else 裡

示範第一次組出來的結構是「if/else 決定方波 → else 底下接正弦、隨機、印出、推進相位」。
看起來很自然，實際產生的 C++ 是：

```cpp
if (angle < 180) {
  square = 100;
} else {
  square = 0;
  sine = ...;      // ← 只有 angle >= 180 的那一半會跑到
  noise = ...;
  Serial.print(...);
}
```

**半個週期完全沒有資料**。程式能編譯能執行，只是圖表少了半圈。
正確做法是把後續步驟接在 **if 區塊的 `next`**（兩條分支之外）。
這個缺陷是靠**整段產碼快照**抓到的 —— 逐行 `toContain` 完全看不出「少了一個大括號」。

#### 踩到的坑 7：Blockly 沒有三運算子積木

想把方波寫成 `angle < 180 ? 100 : 0`，但 `logic_operation` 的選項只有 AND／OR，
寫 `<field name="OP">IF</field>` 會得到兩條載入警告
（「Cannot set the dropdown's value to an unavailable option」與
「Ignoring non-existent input C」）。改用 `controls_if` 的 if/else 兩段式。

#### 踩到的坑 8：產碼快照必須先移除 ID marker 與行尾空白

Blockly 產生器會在變數名後插入 `/* // __BLOCKLY_ID:… */`，
把 `sin(angle / 180.0 * PI)` 拆成 `sin(angle` + marker + `/ 180.0 * PI)`。
語意相同但字串比對必失敗 —— 容易誤判成「generator 產錯了」。
移除 marker 後還會留下多餘的行尾空白，需一併收掉再做整段比對。

### 技術深挖 (Technical Deep Dive)

#### `decode_output` 永不使用 U+FFFD —— HEX 模式的真正價值不在「避開亂碼」
我原本在測試裡斷言「文字模式會出現 U+FFFD、HEX 才看得到」，測試失敗了。
`encoding.rs` 的 fallback 鏈（UTF-8 → Big5 → GBK → 1252 → latin-1）**保證**
「永不產生 U+FFFD、不丟任何位元組」—— 這是刻意的設計（`runner.rs` 的註解
明說：整份輸出消失比亂碼更難診斷）。

代價是**猜測編碼**：`0xFF 0xFE` 在 latin-1/1252 下看起來像合法的「ÿþ」，
學生會誤以為板子真的印了這些字。**HEX 模式的價值是顯示未經猜測的原始位元組**，
這才是除錯時唯一可信的資訊。測試因此改為斷言 `format_line(raw, false)
!= format_line(raw, true)`，並額外鎖定「對有效 UTF-8 兩者語意一致」。

**教訓**：延伸既有模組的語意前，先讀它的設計理由，不要憑直覺假設。

#### `LineFramer` 必須回傳位元組而非字串
初版 `push()` 回傳 `Vec<String>`（已解碼），HEX 模式再 `as_bytes()` 重編碼。
這在 Big5/binary 資料上會失真 —— HEX 就失去了意義。改成 `Vec<Vec<u8>>`，
讓解碼成為**顯示層的最後一步**。

#### `pump` 泛型化 `Read` 才能測試
真實 `SerialPort` 不可在測試中建立（需要硬體）。泛型化後測試餵入
`Cursor`，完整驗證切行、CRLF 跨 chunk、多位元組跨 chunk、停止旗標、
讀取錯誤轉為錯誤行 —— 全部不需要硬體。這比「只測純函式」涵蓋更多。

#### `setBaud` 未連線時不發動後端
序列埠 baud 在開啟時綁定，但**未連線時根本沒有序列埠**。此時呼叫後端只會
得到 `SERIAL_ERROR_NO_PORT`。正確做法是只更新前端狀態，等使用者開啟時套用。

#### 序列埠是獨佔資源 —— Monitor 與 avrdude 不能共存
Windows 上同一個 COM 埠只能被一個程序開啟。`AppState::port_lease` 原本
只服務 upload，現在 Monitor 也用同一把鎖：
`upload_start` 前 `release_port_for_upload()` 取走 session 並清空 lease，
上傳終態 `release_port()` 之後才重連（含 150ms 冷卻 —— Windows 驅動釋放
handle 需要時間，立刻重開會得到 `AccessDenied`）。

`monitor_wants` 記錄「使用者想監看的設定」而非「是否連線」：若只有後者，
上傳結束後就分不清「使用者要重連」與「使用者已手動關閉」。

#### 兩次工具插入都被 `insert_line` 破壞了檔案結構
`insert_line` 在指定行**之前**插入。第一個 `MonitorStatus::connected()`
函式體被硬生生截斷（後面直接接上 `LineFramer` 的 struct 定義），
Rust 報出一連串莫名其妙的 `E0560: struct MonitorStatus has no field named hex`。
第二次更嚴重：整個檔案被壓成一行（`Set-Content -NoNewline` 造成），
需要刪除重建。

**教訓**：插入點必須放在一個完整區塊的邊界（下一個 `///` 註解或 `}` 之後），
且插入後立刻讀回檔案確認結構，**不要**假設行號對齊。
另外含中文的檔案不可用 PowerShell `Set-Content` 改寫（見 2026-09-27 記錄）。

#### E2E mock 缺 `get_serial_ports` 讓序列埠下拉永遠是空的
`board-detector` 的啟動快照走 `get_serial_ports`，而 Tauri mock 只處理了
`refresh_serial_ports`。症狀是「按了開啟監視器卻說沒有埠」——
看起來像功能壞了，實際上是測試環境少了背景資料。

除錯花了三輪才定位，過程本身就是教訓：
1. 先懷疑模組邏輯（讀 `start()`、`toggle()`、`toolbar.js` 的條件）—— 都正確
2. 在測試裡塞 `debug` 欄位印出 `port` / `options` / `calls`，
   發現 `options=[""]`、`calls=[]` —— **一個 invoke 都沒發**
3. 讀 `board-detector.init()` 才發現：mock 的 `get_serial_ports` 沒被
   `__MOCK_CLI_CALLS__` 白名單記錄，看起來像沒被呼叫

**教訓**：新增依賴既有基礎設施的功能時，mock 必須**盤點**該設施的所有
入口（啟動快照 vs 事件推送），不能只補新功能直接呼叫的那一個。
另外，「症狀在 A 功能、原因在 B 模組」時，**先印出實際狀態再讀碼碼**，
靠通讀原始碼找 bug 會在正確的程式碼上繞圈。

#### Playwright 點不到收合的終端機面板內的按鈕
序列控制列位於 `#terminalArea` 內，面板預設收合，位於 Blockly 工作區之下。
Playwright 的點擊被 `blocklyScrollbarHorizontal` 攔截而逾時。

**教訓**：新增位於可收合面板內的互動元件時，E2E 必須先展開面板；
這類「看得見（`toBeVisible` 通過）但點不到」的情況，`click()` 的錯誤訊息
才會指出真正的攔截者。

#### E2E mock 的 TDZ bug 讓 17 個 board-picker 測試全數失敗
這是本輪最難的 bug，除錯花了 5 輪。症狀是「我新增的序列埠 mock 讓
`board-picker` 面板清單變空」，但 `board-picker` 根本不讀 `ports`。

**根因**：`tauri-mock.js` 的 `invoke()` 原本在白名單區塊內才宣告
`const cli = window.__MOCK_CLI__`。我為了讓 `get_serial_ports` 也能用 `cli.ports`，
把該行**移到了白名單之前** —— 於是每次 invoke 都會在讀到 `cli` 時撞上
**TDZ（暫時死區）**，整個 mock 的 `invoke` 直接拋錯，所有 E2E 全滅。

**定位手法**：`git stash push -- <單一檔案>` 逐一還原，二分出真正的變因。
在「症狀在 A 測試檔、原因在共用 mock」的狀況下，這比讀碼碼快得多。

**教訓**：
1. 把變數宣告**往上移**看似無害，實質改變了拋錯時機。
   在 JS 裡 `const` 是 block-scoped，跨區塊「借用」在位置改變後會變成 TDZ。
2. 改動**共用測試基礎設施**時，要預期影響範圍遠大於新增功能本身。
   本輪新增序列埠 mock，卻連帶打斷 17 個既有測試 —— 這是共享 mock 的固有風險。

#### 診斷碼要留到最後才加，且要能自我證偽
前四輪我都在讀 `start()` / `toggle()` / `board-detector.init()` 的原始碼，
試圖用「讀懂程式」找出 bug —— 但 bug 在**測試 mock**裡，不在被讀的檔案。
直到加了 `console.log` 印出 `mockPorts` 與 `getState().ports` 的落差，
才把問題從「序列監視器」縮小到「board-detector 從未收到快照」。

**教訓**：症狀與原因分處不同檔案時，**先量測再閱讀**。
印出兩個來源的實際值，一次就鎖定邊界。

#### `installTauriMock` 的 `cli` 參數從未傳入頁面（既有缺陷）
寫「沒有序列埠」的測試時，傳了 `{ cli: { ports: [] } }` 卻完全無效。
原因是 `addInitScript` 只傳了 `{ files }`，`config.cli` 在頁面內恆為
`undefined`，`Object.assign(defaults, config.cli || {})` 退化成只留預設值。

這是**本輪之前就存在**的缺陷，只是先前沒有測試傳入 `cli`，所以從未暴露。
修正後 `board-picker` 與 `compile-flow` 的既有測試也受惠（它們同樣可以
傳入 `cli` 覆寫）。

**教訓**：公開參數若沒有測試覆寫，就等於不存在。
新增 helper 參數時，應立即補一個「參數確實生效」的測試，
否則它會靜默失效直到有人誤用它。

#### 「依狀態停用」不等於「尚未實作」
`toolbar.spec.js` 的契約是「工具列不得有未實作的停用按鈕」。
`btn-serial-send` 在未連線時停用被誤判為未實作。

**判準**：registry 的 `implemented` 表達「這個按鈕有沒有處理器」，
DOM 的 `disabled` 表達「現在能不能按」。兩者語意不同，把狀態停用算進
未實作，會逼出一個「永遠能按但送不出東西」的按鈕 —— 那才是真的無反應。

- `npx vitest run tests/unit`：**168 passed**（+2）

## 2026-09-28：實機除錯（二）—— 埠未釋放與 baud 錯誤無反應

### 使用者回報（第一輪修正後）

1. ✅ 可以開啟監視器，燈號反應正確，`Serial.print()` 正確
2. ❌ 再次按上傳，**沒有自動先關閉**；手動關閉再上傳，失敗：「無法開啟序列埠」
3. ❌ 切 baud：「無法開啟序列埠」。手動先關再切再開可成功，
   但 **baud 錯誤時不會 dump 亂碼**，要切回正確 baud 後才看到上次的亂碼

### 根因 ①：stop 只設旗標，沒有等待 thread 結束 → handle 未釋放

`stop_monitor()` 與 `release_port_for_upload()` 原本都只做 `session.request_stop()`
就回傳。此時讀取 thread **仍活著**，`SerialPort` 仍持有 Windows 的 COM handle。

Windows 上序列埠是獨佔資源，handle 未釋放時 `open()` 必定 `AccessDenied`：

| 症狀 | 觸發路徑 |
|---|---|
| 上傳前沒自動關閉 | `release_port_for_upload` 設旗標就返回，avrdude 隨即 `open()` 撞上佔用 |
| 手動關閉後仍無法開啟 | `stop_monitor` 同樣沒等 thread 結束 |
| 切 baud 無法開啟 | `setBaud` 的 stop→start 太緊接，舊 handle 還在 |

**修正**：
- `AppState` 新增 `monitor_thread: Arc<Mutex<Option<JoinHandle<()>>>>`
- `start_session` 保存 handle
- `stop_monitor` / `release_port_for_upload` 都 **join** 後才回傳
- join 後加 `PORT_RELEASE_COOLDOWN_MS = 120ms` 冷卻 ——
  join 只保證 Rust 側 drop，Windows 驅動釋放 handle 還需要時間

### 根因 ②：baud 錯誤時資料卡在 `LineFramer` 緩衝

`LineFramer` **只在遇到 `\n` 才吐出行**。baud 設錯時位元組邊界錯位，
換行符（0x0A）極少出現，於是所有資料永遠卡在緩衝裡。
使用者看到的就是「切錯 baud 毫無反應，切回來才看到累積的亂碼」。

**修正**：新增 `IDLE_FLUSH_MS = 250`。資料抵達後若這段時間內沒有新資料，
強制把殘餘位元組當成一行輸出（對齊 Arduino IDE serial monitor 的行為）。

### 根因 ③：「上傳暫停中」顯示成「未連線」

使用者說「沒有自動先關閉」是因為**他看到狀態燈顯示「未連線」**，
以為自動暫停沒發生。其實有暫停（只是當時的問題是 handle 未釋放），
但顯示上完全無法區分「上傳暫停中（會自動接回來）」與「使用者關掉了」。

**修正**：後端在暫停時送 `error: "SERIAL_PAUSED_FOR_UPLOAD|"`；
前端據此新增 `pausedForUpload` 狀態，狀態燈改為三態
（`已連線` / `上傳暫停中` / `未連線`，`data-connected` 為 `true`/`paused`/`false`）。

### 技術深挖 (Technical Deep Dive)

#### 「設定旗標」不等於「資源已釋放」
我原本的 `stop()` 直覺上就是完整的停止動作。但跨程序資源（檔案、序列埠、
socket）有兩層：設定旗標只是**請求**，必須等持有者**歸還**才真正釋放。
`JoinHandle` 存在的唯一理由就是提供這個「等待歸還」的能力。

**教訓**：凡是需要釋放 OS 資源的元件，停止路徑必須有「等待歸還」這一步，
不能只靠旗標。Rust 的 `JoinHandle::join()` 與 `Drop` 語意讓這件事很直覺，
但在 Tauri command 裡很容易忘記把 handle 存起來。

#### 第一次寫的測試是**假綠**的
`pump_flushes_a_line_that_never_ends_with_newline` 初版讓假 reader 在
資料送達後回 `Ok(0)`，結果 `pump` 結束時既有的 `flush()` 就會吐出殘餘
—— 測試通過，但**沒有驗證到我要的閒置強制輸出**。

改成：假 reader 送一次資料後**永遠回 `TimedOut`、永不回 `Ok(0)`**，
在另一個 thread 跑 `pump`，主執行緒 sleep 300ms 後就檢查有沒有輸出。
這次真的失敗了，修正才有意義。

**教訓**：寫測試時要問「這個測試在**修正前**會失敗嗎？」。
如果一個測試無法區分「正確實作」與「碰巧也會通過的舊實作」，它就沒有價值。

#### 跨語言的錯誤語意：Rust 的 `Err` 不等於「失敗」
`Err(TimedOut)` 在 `serialport` 的語意是「這次沒資料」，
在 `std::io` 的一般慣例裡卻是「操作失敗」。照搬直覺會造成
「板子安靜 50ms 就被當成斷線」這種離譜行為。

**教訓**：使用外部 crate 時，先讀它的文件確認**錯誤值的語意**，
不要假設 `Err` 就是「壞掉了」。

- `npx playwright test --workers=1`：**120 passed**（全數通過）

## 2026-09-28：實機除錯（三）—— 四項回報的修正

### 使用者回報

1. 「連按 2 次上傳鈕有保護嗎？」
2. 「上傳有自動切回失效狀態的『開啟監視器』按鈕及暫停燈號，但上傳成功後沒有自動切回連線狀態」
3. 「程式設 9600，用 115200 看，沒有亂碼及任何訊息，使用者可能誤會沒有輸出」
4. 「監看時收面板，畫面沒有更新，所佔區域沒有重繪還給工作區」

### ① 連按上傳鈕：保護有，但看不出來

`run()` 第 336 行 `if (busy) return Promise.resolve(false)` **單飛保護一直是有效的**。
問題在於沒有視覺回饋 —— 使用者以為按鈕壞掉而反覆點擊。

**修正**：`main.js` 訂閱 `CodeBridgeCompile.onChange`，把 `#btn-run` 的
`disabled` 與 `aria-busy` 綁到 `state.busy`。

### ② 上傳後沒切回「已連線」

`start_session()` **從未送出「已連線」狀態**。上傳後自動重連走的是這條路徑，
所以前端狀態燈永遠停在「上傳暫停中」、按鈕停在失效的「開啟監視器」。

**修正**：
- `start_session` 成功後 emit `SERIAL_STATE(connected: true)`
- 重連**失敗**時 emit `SERIAL_STATE(failed)`，不再靜默

### ③ 錯誤 baud 沒有訊息 —— 這不是 bug，是 USB-UART 的物理特性

關鍵發現：**CH340 之類的 USB-UART 晶片會硬體重組時脈**。
板子以 9600 送，PC 端開 115200，**收到的仍是正確文字而非亂碼** ——
晶片已經把 9600 的位元組重組好才送 USB 封包。

所以「沒有亂碼」是**正確行為**。使用者看不到訊息的真正原因是
**開機訊息在他開啟監視器之前就印完了**。

**修正**（新增功能）：
- `MonitorConfig.reset_on_open` + `serialport::dtr_on_open(false)`
  —— UNO／Nano 的 reset 電路透過 DTR 觸發，開啟時讓板子重啟並重播開機訊息
  （對齊 Arduino IDE 開啟 Serial Monitor 的行為）
- UI 開關「開啟時重啟板」（預設關閉：使用者可能已在跑程式）
- 獨立按鈕「重新啟動開發板」（僅已連線時可用）
- i18n 提示說明「若一直看不到輸出，多半是程式只在開機時印一次」

### ④ 收合終端機面板不重繪 Blockly

終端機面板位於 `#blocklyArea` **內部**，收合改變了工作區的可用高度。
但 Blockly 的 SVG 只在 `inject()` 時量一次尺寸，不會自己察覺容器變化。
程式預覽面板（`initCodeToggle`）一直有呼叫 `svgResize`，**終端機面板漏了**。

**修正**：`terminal-panel.js` 新增 `onWorkspaceResize(listener)`，
`setOpen()` 在切換後 emit；`main.js` 註冊為 `Blockly.svgResize`。

### 技術深挖 (Technical Deep Dive)

#### 「沒有亂碼」不等於「壞掉了」—— 先確認物理特性再改程式
一開始我以為閒置 flush 的閒置時間不夠短，延長了它。讀 `serialport` 原始碼時
才發現真正的原因在晶片那一端。**延長閒置時間不會解決「開機訊息早已印完」**。

**教訓**：症狀描述（「沒有亂碼」）往往不是根因。遇到「預期會有 X 卻沒有 X」時，
先確認 X 在當前的技術前提下**是否真的會出現**。

#### 契約測試會擋下「靜態 disabled」這個反模式
新增 `btn-serial-reset` 時我直覺加了 `disabled`（初始未連線），
`toolbar-buttons.test.js` 立刻擋下 —— 靜態 `disabled` 與
registry 的 `implemented: true` 契約衝突。

正確做法是**不寫 HTML `disabled`**，改由執行期 `syncControls()` 設定。
這同時改善了 UX：使用者不會看到一個「天生灰掉」的按鈕而以為尚未實作。

#### `serialport` 4.x 沒有 `set_dtr`，但有 `dtr_on_open`
原本預期要開 `unstable` feature 才能操作 DTR，實際上 4.9.0 已把它收進
Windows 後端，只在 builder 上留下 `dtr_on_open(bool)`。
**讀原始碼比猜測 feature gate 快得多**（`Get-ChildItem` + `Select-String`）。

## 2026-09-28：實機除錯（四）—— `disabled` 對 div 無效 + 位元組診斷

### 使用者回報

1. 「115200 還是看不到 9600，印出空白行，重啟板子也是一樣」
2. 「上傳鈕只會執行一次，OK，但**不會變灰**，可重複按，但不會重複觸發」

**修正**：`#btn-run` 改為 `<button type="button">`，並在 `.toolbar-btn`
補上 `background/border/padding/font/color` 的 reset（否則會露出瀏覽器預設樣式）。
同時加了契約測試鎖住「`#btn-run` 必須是 button」——這個坑很容易再踩。

### ①③ 「印出空白行」：無法診斷 → 讓它可診斷

**這不是 bug，是資訊不足。** 使用者看到空白行時，畫面完全無法分辨兩種情況：

| 情況 | 原因 | 需要怎麼修 |
|---|---|---|
| 0 bytes | 板子根本沒送資料（程式沒印，或 DTR reset 沒觸發） | 改程式或改硬體行為 |
| >0 bytes 但看不到字 | 解碼或波特率問題 | 調設定 |

**沒有這個數字，就只能在兩個假設之間來回猜。**

**修正**：
- `pump` 的 sink 改為 `FnMut(Vec<String>, u64)`，帶出累計位元組數

新增的位元組計數正是為了區分這種情況：

- 顯示 **「等待資料…」**（0 bytes）→ 板子真的沒送，

- 顯示 **「已接收 N bytes」** 但沒字 → 是解碼問題

## 2026-09-28：實機除錯（五）—— 更正一個錯誤判斷 + 控制字元可見化

### 使用者回報（關鍵診斷資訊）

> 「執行範例的 Serial Hello, 9600 baud，監視器用 115200 收，
> 上方有『已接收 N bytes』，但**文字空白**」
>
> 「按重啟可重新計算 N bytes，但按 reset 或重開面板不會」

### ⚠️ 我必須更正之前的錯誤判斷

前三輪我反覆寫著：

> 「CH340 之類的 USB-UART 晶片會**硬體重組時脈**，所以 PC 端用錯誤的 baud
> 讀到的**仍是正確文字而非亂碼**。」

**這是錯的。** CH340 是真正的 UART-to-USB 橋接器 ——
PC 端設定的 baud rate 會透過驅動程式下發給晶片，設定它的**取樣時脈**。
baud 不符時，CH340 以錯誤的時脈取樣 UART 線路 → **產生垃圾位元組**。

「N bytes 但文字空白」正是 baud 不符的**典型症狀**，與我先前的斷言相反。
這個錯誤判斷讓我前兩輪的除錯方向偏了 —— 幸好位元組計數的引入
才讓真相浮現。

### 真正的根因：解碼鏈的 fallback 把垃圾變成了「看不見的字元」

`decode_output` 的 fallback 鏈（UTF-8 → Big5 → GBK → 1252 → latin-1）
**設計上是「永不失敗、永不丟資料」**（見 `encoding.rs` 的設計說明）。
問題是 **Big5 解碼器是總函式** —— 任何位元組序列都能「成功」解碼。

所以 baud 不符產生的垃圾位元組被「成功」解成**控制字元**（0x00–0x1F），
而這些字元**在終端機裡完全不可見** → 使用者只看到「空白行」。

這個設計對編譯器輸出是**正確的**（寧可亂碼也不要整份輸出消失），
但對序列監視器是**有害的** —— 它把「波特率不符」這個明確的錯誤
轉換成了「什麼都沒有」，讓問題**無法被診斷**。

### 修正：讓不可列印字元可見

新增 `make_control_chars_visible()`：把 C0 控制字元、刪除字元、
C1 控制區轉成 `<0xNN>` 佔位符。效果：

| 情境 | 修正前 | 修正後 |
|---|---|---|
| 波特率不符 | 空白（無法診斷） | `<0x00><0x01><0x1B>…` → 一眼看出是 baud 問題 |
| 正常輸出 | 正常 | 正常（不變） |
| tab | 保留 | 保留（不變） |

**這是把不可診斷的症狀轉成可診斷的關鍵** —— 學生看到 `<0x00>` 會知道
「板子有在送東西，但送的不是文字」，而不是懷疑自己的程式。

### 關於「按 reset 不會重算 N bytes」

**這是正確行為**，不是缺陷。位元組數是「本次連線累計」，
按實體 reset 不會重啟我們的 session，因此不歸零 —— 這符合
「累計值」的語意。只有「重新開啟監視器」才會開新 session 並歸零。

### 技術深挖 (Technical Deep Dive)

#### 錯誤的斷言會讓除錯方向整體偏掉
我連續兩輪基於「CH340 會重組時脈」這個**未經驗證的假設**做決策，
還把它寫進計畫文件當成「已確認的技術判斷」。若非使用者提供了
「N bytes 但空白」這個具體觀察，這個錯誤會持續誤導後續修正。

**教訓**：寫下「這是硬體特性所以如此」之前，先確認它**真的是硬體特性**。
特別是當同一個症狀有更簡單的解釋時，優先檢查自己的程式是否製造了症狀。

#### 「防禦性程式碼」有時會製造診斷障礙
`decode_output` 的 fallback 鏈是刻意的防禦性設計 —— 但對**互動式顯示**而言，
「永遠給我點什麼」反而比「老實說我解不出來」更糟，因為它掩蓋了問題。

**教訓**：容錯策略必須**依使用情境**決定。批次處理的日誌輸出適合
「永不失敗」；互動式的序列監視器應該「誠實顯示原貌」。

**提問 2 直接命中我在第一輪就埋下的錯誤決策。**

我讓序列監視器複用 `encoding.rs` 的 `decode_output()`，理由是「統一解碼策略」。

`0xA4 0xA4` 在 Big5 是「中」，在 latin-1 是 `¤`。

## 2026-09-28：實機除錯 —— Monitor 一開啟就死掉

### 使用者回報的現象

```
開始上傳到 COM4，請勿斷開連線....
New upload port: COM4 (serial)
上傳成功
SERIAL_ERROR_READ|Operation timed out
Serial.println() 無資料印出
終端面板上方一直顯示「未連線」
```

### 根因：`Err(TimedOut)` 被當成「板子斷線」

`SerialPort::timeout(50ms)` 到期時，`read()` 回的是 **`Err(TimedOut)`** ——
它語意上是「這次沒資料」，不是「失敗」。這正是設 timeout 的目的：
讓讀取能週期性返回，呼叫端才檢查得到 stop 旗標。

我在 `pump()` 裡把所有 `Err` 一律當成讀取錯誤並 `break`。結果是：

**板子只要安靜超過 50ms，Monitor 就死掉。** 燒錄完晶片重啟的那幾秒
沒有任何序列輸出，於是使用者看到「上傳成功 → 立刻斷線 → 永遠沒有輸出」。

這也解釋了為什麼單元測試全過：測試用 `Cursor` 永遠回 `Ok(size)` 或
`Ok(0)`，**從未回過 `Err`**。真實序列埠才會有這個行為。

### 修正

新增 [`is_no_data()`](../../src-tauri/src/serial_monitor.rs) 區分兩者：

```rust
pub fn is_no_data(err: &std::io::Error) -> bool {
    matches!(err.kind(),
        std::io::ErrorKind::TimedOut | std::io::ErrorKind::WouldBlock)
}
```

`pump()` 對 `is_no_data` 走 `continue`（繼續輪詢），其餘仍視為真斷線。
`WouldBlock` 一併涵蓋，因為 Unix 與部分驅動在非阻塞模式回的是它。

### 附帶修正：重連時 HEX 設定遺失

`start_session(..., hex)` 的 `hex` 在 upload 重連路徑被寫死成 `false`。
使用者選了 HEX，燒錄一次後設定就悄悄消失了。

**修正**：`hex` 移進 `MonitorConfig`（它是「想監看的設定」的一部分，
與 `port`／`baud` 同級），`start_session` 改從 config 讀取。

### 技術深挖 (Technical Deep Dive)

#### 假讀取器測不出「逾時」語意 —— 這類缺陷只能靠實機抓
`Cursor` 永遠不會回 `Err(TimedOut)`，所以 `pump()` 的錯誤分支在測試中
從未被正確觸發。**測試替身越「完美」，越測不出真實 I/O 的邊界行為。**

修好後我補了三項測試鎖定此語意，且刻意設計成**會回 `Err`** 的假 reader：
- `pump_treats_timeout_as_no_data_not_disconnect`
- `pump_treats_would_block_as_no_data`
- `is_no_data_only_covers_polling_results`（明確斷言 `BrokenPipe`／`NotFound`
  **不**算「沒資料」，否則拔線時會無限重試、永遠顯示已連線）

**教訓**：為 I/O 迴圈寫測試時，替身必須涵蓋**真實世界的失敗模式**，
而不只是成功路徑。

#### 測試不要用 stop 旗標控制迴圈收尾
初版測試讓假 reader 在資料送達後由 sink 設 stop 旗標來收尾，結果
`pump` 在 flush 前就 break，收集到 32 份重複的 `"LED on"`。
改用「最後一次讀取回 `Ok(0)`」模擬串流結束，**測試便與實作時序解耦**。

**教訓**：讓測試去操控被測對象的內部旗標，會把測試綁死在實作的時序細節上。
用 I/O 本身的語意（`Ok(0)` = EOF）收尾更乾淨。

### 技術深挖 (Technical Deep Dive)

**為什麼不能把裝置狀態寫進 .cbg**

原來痛點是「啟動時 UI 顯示 COM4，上傳卻報尚未選擇序列埠」。根因不是任何一邊會歸零，而是**兩個來源看不一樣**：

| 來源 | 讀什麼 | 性質 |
| --- | --- | --- |
| 下拉 `#serial-selector` | 使用者眼前看到的值 | 真值，但不永久 |
| `meta.port` | 對象打檔瞬間 | 可能老化 |

`pullInitialPorts` 只在下拉值「變化」時才寫入 meta，而使用者手動選了同一個埠時
value 未變，導致 meta 不受更新，上傳拒絕。

新設計把裝置狀態從檔案移置來源，下拉就是唯一來源。偏好埠則改存 localStorage

**為什麼範例改用 Rust 掃描而非保留 manifest.json**

靜態檔案伺服器沒有「列出目錄」的 API，`fetch('examples/')` 拿不到檔案清單。舊方案必須手維
一份 `manifest.json`，這裡每新增一個範例就要調維統一份檔案——而且遺忘更新。
改用 Tauri 資源目錄後 `fs::read_dir()` 真的能列檔，並取代磁碟上的前綴排序，常數就是
正規方式。

全空時回傳存在的目錄，讓錯誤訊息指出真正該修哪裡。

### 技術深挖 (Technical Deep Dive)

**「單一來源」的重整不等於自動消滅第二個來源**

metadata 重整時我移除了 `board-detector` 對 meta 的寫入，卻忘了
`board-picker` 還在寫。移除一條路徑不等於建立單一來源——必須同時確認**所有**
寫入者都改到新去處，否則只是把不一致換個方向。

更深的教訓是自動偵測不能當作唯一真相：後端認不出 clone 板時自動偵測本來就是空的，

不能想著「反正會自動偵測」。

**空殼目錄：存在 ≠ 可用**

`is_dir()` 只能證明目錄存在，不能證明裡面有東西。資源掃描類的程式碼要用
「內容符合預期」當判準。這個陷阱特別容易出現在 build 工具產生的中間目錄上。

### 修正一：`Serial.begin` 預設鮑率 9600，清單順序不動

### 修正二：程式預覽面板加行號

`style.css` 的 `#codeContent` 早就有 `counter-reset: line`（有人開頭沒做完）。
補上 `.code-line { counter-increment: line }` 與 `.code-line::before` 即可。

1. `innerHTML` 仍只含高亮後的程式碼，不會混入行號文字
